# Gomoku

15 × 15 Gomoku. Starting from two current conversations invites them directly. With fewer than two, the picker fills the missing player from conversations or **You**. The program randomly assigns Black and White on the first round and whenever either player changes. Another round with the same pair swaps their previous colors, regardless of participant ordering. Each player receives a private invitation naming their assigned color and confirms readiness. Both ready starts a persisted three-second countdown; cancelling readiness cancels it without changing colors. Black moves first. Models use authenticated interfaces; human controls affect only the human's own seat and turn. The next player receives a directed action request; the result is broadcast. Reloading or restarting restores a paused board; continuing resumes it, while explicitly closing the tab resets it.

Two independent player cards show the real model name, model-brand artwork, conversation and side. They stay 192px high through invitation, readiness, countdown, moves and results. At widget widths of 680px or more they sit to the right of the board; narrower views put them above it. The light background is pure white; the dark background matches Pudding conversations. Controls use neutral gray. Unassigned sides show a dashed circle and “Undecided”. The active player shows an elapsed turn clock backed by the saved turn-start timestamp. Comments appear only inside the cards, in a compact two-line box with the move number inline before the sentence. `placeStone` accepts an optional comment of up to 40 characters, committed with the legal move; the player's next move replaces it. Humans can compose a comment in their card before clicking an intersection.

The move-number toggle is off by default and labels occupied intersections in chronological order. With numbers visible, a ring marks the latest stone without covering its number. After a finished game with at least one move, Replay opens at the empty board: previous/next buttons and a slider review the score, including the comments in the existing player cards. Back to result restores the final board. Replay and number visibility are local viewing controls; they never write game state, change its version, or send notifications. Starting another round exits replay. Card and board geometry stays fixed throughout viewing.

`placeStone` takes real board coordinates, e.g. `{ "column": "H", "row": 8, "comment": "Center opening" }`. Columns are uppercase **A–O**; rows are numbers **1–15**, with **1 at the bottom and 15 at the top**. Numeric columns are rejected. Board reads and notifications use the same coordinates: `board.text` is one multiline string with the letter header and rows 15 down to 1; the opt-in `history` is the chronological list of `{column,row,stone:"B"|"W",comment?}`; `moveCount` counts individual placements. The history is canonical; numeric rendering cells, current turn, winner, last move and latest card comments are derived. Readiness responses include the caller's identity, readiness and `yourTurn`.

Pause cancels only this game's model work, blocks human and model moves and freezes thinking time. Continue retains the game, resumes pending work, and sends a fresh action request only if an earlier model attempt ended without completing its business action. New game is available while paused: keep the two players, retire old requests, swap colors, reset readiness/history, then prepare and count down again. Change players is available while paused or after the result and opens the picker with the existing pair selected; changing either player draws colors afresh. Pause/continue retains assigned colors. A resumed countdown restarts at three seconds. Each source revision has its own page state; old-format games stay with their old revision, and the new revision starts a fresh game.

The game follows Pudding's Simplified Chinese, Traditional Chinese or English setting live without changing the game state. Visible game errors also follow language changes; interface errors use the language at invocation. Result messages reuse the localized summary, while structured game values stay unchanged. Installed names and existing player comments remain as authored, including literal dollar signs and braces in names. Notification receipts retain their original text across language changes.

Interfaces are called through `widget_invoke({targetID, expectedStateVersion, name, input})`, not standalone tools. Invitations explain the wrapper, the assigned color, readiness (`ready`), and conceding (`resign`, input `{}`). A seated player may resign during either player's turn; both receive the result. There is no timeout forfeiture.

Notifications contain the current board, last move, move count, turn, winner, round and phase, without history. `placeStone` and `resign` return only the last move, move count, turn, winner, round and phase; the host adds `stateVersion`. `readBoard` defaults to the current board and participant/seat state; explicitly pass `{includeHistory:true}` to retrieve the full chronological history with comments. Successful readiness operations also omit history. `stateVersion` versions all page state for concurrency checks; `moveCount` alone counts stones. A model can play directly from its notification, without observing or reading again each turn. Stale versions are still rejected before an action runs.

Player identity precedes side and status in document reading order, while the visual card layout remains unchanged. Opening hints distinguish the assigned color, waiting for that player's readiness, waiting for the opponent, and both players ready.

Requires source-package format 2, protocol 24 (host locale and candidate model metadata) and SDK 1. See [development guide](../../docs/widget-development.md). The initial public package is 1.0.0. Unreleased history was reset before production; installed development items are untouched. Future formal releases remain immutable; each source revision has its own page state.
